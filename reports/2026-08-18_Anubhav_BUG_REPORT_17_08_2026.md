## 1. What the bug is

On the dashboard at **https://login.24observe.com/settings**, the **Connections** section is intended to let a logged-in user connect (or sign in with) external identity providers — **Google** and **GitHub**. When the user clicks the connect/sign-in button in that section, the page issues a request to:

```
GET https://api.24observe.com/api/v1/me/oauth/google/start
```

The API responds with **HTTP 401 Unauthorized**, and the page shows "Unauthorized" to the user. The OAuth connect flow never starts.

This is the same behavior for both providers:
- `GET /api/v1/me/oauth/google/start` → **401 Unauthorized**
- `GET /api/v1/me/oauth/github/start` → **401 Unauthorized**

---

## 2. Root cause — wrong API path

The OAuth endpoints are **not** under `/api/v1/me/oauth/...`. Per the published OpenAPI spec (`https://api.24observe.com/openapi.json`), the OAuth start/callback routes are mounted under **`/api/v1/auth/...`**:

```
GET /api/v1/auth/google/start     → Read auth google start
GET /api/v1/auth/google/callback  → Read auth google callback
GET /api/v1/auth/github/start     → Read auth github start
GET /api/v1/auth/github/callback  → Read auth github callback
```

The dashboard's Connections section calls `/api/v1/me/oauth/{provider}/start`, which is **not a registered route**. The platform's auth middleware sees an unrecognised path under the authenticated `/api/v1/me/` namespace and returns **401 Unauthorized** (instead of a 404) — masking the real problem (the route simply doesn't exist).

### Why it 401s instead of 404s

The `/api/v1/me/*` namespace requires a valid session/PAT. The non-existent `/me/oauth/...` path falls into that protected namespace, so the middleware rejects the request with **401** before ever reaching route resolution. A truly non-existent route outside the protected namespace (e.g. `/api/v1/connections`) returns **404** — see evidence below.

---

## 3. Evidence — HTTP probes

### 3.1 The failing path (what the dashboard calls)

| Request | HTTP status | Meaning |
|---------|-------------|---------|
| `GET /api/v1/me/oauth/google/start` | **401 Unauthorized** | Path doesn't exist; rejected by auth middleware |
| `GET /api/v1/me/oauth/github/start` | **401 Unauthorized** | Same |

### 3.2 The correct path (from the OpenAPI spec)

| Request | HTTP status | Meaning |
|---------|-------------|---------|
| `GET /api/v1/auth/google/start` | **200** — redirects to Google OAuth consent screen (`accounts.google.com/signin/oauth/...`, client_id `869604192787-...`, redirect_uri `https://api.24observe.com/api/v1/auth/google/callback`, scope `openid email profile`) | Route exists and works |
| `GET /api/v1/auth/github/start` | **503 Service Unavailable** | Route exists; GitHub OAuth app appears misconfigured server-side (separate issue), but the route itself resolves |

### 3.3 Control probes (confirming the 401-vs-404 distinction)

| Request | HTTP status | Meaning |
|---------|-------------|---------|
| `GET /api/v1/me` (no token) | **401 Unauthorized** | Known authed endpoint — confirms 401 is the "missing auth" signal |
| `GET /api/v1/me/tokens/` (no token) | **401 Unauthorized** | Same |
| `GET /api/v1/connections` (no token) | **404 Not Found** | Truly non-existent route outside `/me/` — gets a 404 |
| `GET /api/v1/integrations` (no token) | **404 Not Found** | Same |

**Interpretation:** A route that genuinely doesn't exist returns 404. The `/me/oauth/...` path returns 401 only because it sits inside the auth-protected `/me/` namespace — i.e. the dashboard is hitting a path that was never registered, and the middleware is hiding that behind a 401.

---

## 4. The mismatch in one line

```
Dashboard calls:   /api/v1/me/oauth/google/start   → 401  ❌
OpenAPI defines:   /api/v1/auth/google/start       → 200  ✅
```

The dashboard bundle hard-codes the wrong base path (`/api/v1/me/oauth/`) instead of the spec's path (`/api/v1/auth/`).

---

## 5. Impact

- **Feature broken:** Users cannot connect a Google or GitHub account from Settings → Connections. Every click returns "Unauthorized."
- **No workaround in the UI:** There is no alternate button or link that hits the correct `/auth/...` path.
- **Misleading error:** The 401 implies an auth/permission problem (suggesting the user's session is bad), when the real cause is a wrong URL. Users may waste time re-logging-in, regenerating tokens, etc.
- **Scope ambiguity:** It is unclear whether "Connections" is meant to be an *account-linking* feature (attach a Google/GitHub identity to an existing 24observe account) or just a *sign-in* shortcut. The existing `/auth/...` endpoints are sign-in flows (they end at `/auth/{provider}/callback` and set a session cookie) — they do **not** link an identity to an already-authenticated account. If the Connections section is intended as account-linking, then the `/auth/...` endpoints are the wrong fix too: a new `/api/v1/me/oauth/...` (or similar) endpoint set would need to be implemented server-side. Either way, the dashboard is currently calling a path that does not exist.

---

## 6. Recommended fix

### Option A — Fix the dashboard path (if Connections is just a sign-in shortcut)

Change the Connections section's button to call the spec'd endpoints:

```diff
- GET /api/v1/me/oauth/google/start
+ GET /api/v1/auth/google/start

- GET /api/v1/me/oauth/github/start
+ GET /api/v1/auth/github/start
```

This makes Google connect work immediately. GitHub will still 503 until the GitHub OAuth app is configured server-side (separate bug).

### Option B — Implement account-linking server-side (if Connections is meant to attach an identity to a logged-in user)

Add a new set of authenticated endpoints (these do not exist today):

```
GET  /api/v1/me/oauth/{provider}/start      → mint a link-token, redirect to provider
GET  /api/v1/me/oauth/{provider}/callback   → verify, attach provider identity to current user
DELETE /api/v1/me/oauth/{provider}          → unlink provider
GET  /api/v1/me/oauth                       → list linked providers
```

…then keep the dashboard calling `/me/oauth/...`. Without these endpoints, the dashboard's `/me/oauth/...` calls will always fail.

**Decision needed from the 24observe team:** is Connections a sign-in shortcut (→ Option A) or true account-linking (→ Option B)? The current dashboard code implies Option B (it calls `/me/oauth/...`, suggesting a per-user linked-accounts model), but only the Option A endpoints actually exist server-side.

### Bonus — improve the error surface

Regardless of A or B, the auth middleware should return **404** for non-existent routes under `/api/v1/me/...` after confirming the caller is authenticated, rather than blanket-401-ing every unknown sub-path. That would have made this bug fail loudly as "route not found" instead of looking like a permissions problem.

## 7. Severity rationale

Rated **HIGH**:
- The entire Connections feature is non-functional (every click 401s).
- There is no UI workaround.
- The 401 misleads users into thinking their session/token is the problem.

Not CRITICAL: account login itself (email/password) still works; only the OAuth connect/sign-in path from the Connections section is broken.

```powershell

$r4.StatusCode  # 404
```

---

## 9. Verdict

**OPEN / VERIFIED — bug still present.** The Settings → Connections section calls `/api/v1/me/oauth/{provider}/start`, a path that does not exist on the API. The real OAuth endpoints are at `/api/v1/auth/{provider}/start` (per the OpenAPI spec and confirmed by live probe — Google returns a valid OAuth redirect, GitHub returns 503). The dashboard needs its Connections button URL corrected (Option A), or the API needs new `/me/oauth/...` account-linking endpoints implemented (Option B). One of the two is required to make the feature work.
