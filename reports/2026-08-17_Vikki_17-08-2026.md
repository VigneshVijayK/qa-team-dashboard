# Bug Report: Email verification bypass on signup — full account access without verifying email

**Target:** `https://login.24observe.com` (auth backed by `https://api.24observe.com`)
**Severity:** High (auth/registration bypass)
**Date:** 2026-08-17
**Reporter:** vikki
**Reporter notes:** Reproduced via the public API; the dashboard behavior matches. Test account and monitor were cleaned up afterwards.

---

## Summary

When a user signs up at `https://login.24observe.com/register`, the backend hands back a fully-working access token *before* they've verified their email address. That token is good for an hour and works on every protected endpoint I tried — reading account info, listing monitors, and even creating monitors (a write operation). So the "verify your email" step that the product clearly has is effectively optional: anyone can register with a throwaway or completely fake address and use the platform immediately.

What gave it away in the GUI is exactly what the reporter described: first signup drops you straight into `/monitors` and the features all work; but if you come back later and sign in with the same unverified email, you get blocked with "please verify your email before signing in." So verification is enforced on **login** but not on **registration** — which makes no sense, since the first signup session is just as valid as a logged-in one.

## Steps to reproduce

1. Register a new account with any email you don't actually own (must be `>=12` char password per the schema):

```bash
curl -s -i -X POST "https://api.24observe.com/api/v1/auth/register" \
  -H "Content-Type: application/json" \
  -H "Origin: https://login.24observe.com" \
  --data-binary '{"email":"[EMAIL REDACTED]","password":"Bug-Test-Pass-2026!","organizationName":"BugTestOrg_3xdvikby"}'
```

2. Server returns `200 OK` with an `accessToken` immediately — no verification requested:

```json
{"accessToken":"eyJhbGciOiJIUzI1NiJ9...."}
```

Decoding the JWT shows it grants `role: owner` right away, with no `emailVerified` claim:
```json
{"sub":"186","orgId":186,"role":"owner","jti":"9c89ee43-...","iat":1786960909,"exp":1786964509,"aud":"upstat","iss":"upstat"}
```

3. With that token (from an unverified account), call protected endpoints — they all succeed:

```bash
TOKEN="eyJhbGciOiJIUzI1NiJ9...."

# Account + quota — 200 OK
curl -s "https://api.24observe.com/api/v1/me" -H "Authorization: Bearer $TOKEN"

# List monitors — 200 OK, x-total-count: 0, body []
curl -s "https://api.24observe.com/api/v1/monitors" -H "Authorization: Bearer $TOKEN"
```

4. Even a write works — create a monitor with the unverified token:

```bash
curl -s -i -X POST "https://api.24observe.com/api/v1/monitors" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  --data-binary '{"name":"BugTest Monitor","url":"https://example.com","type":"https","intervalSec":300,"timeoutMs":10000}'
```

Response: `HTTP/1.1 201 Created`
```json
{"id":728,"organizationId":186,"name":"BugTest Monitor","url":"https://example.com","type":"https","intervalSec":300,...}
```

So an unverified account can not only *read* protected data, it can mutate state and consume plan quota.

5. For contrast, now try logging in with the same email/password (this is the "second time it blocks me" the reporter saw):

```bash
curl -s -i -X POST "https://api.24observe.com/api/v1/auth/login" \
  -H "Content-Type: application/json" -H "Origin: https://login.24observe.com" \
  --data-binary '{"email":"[EMAIL REDACTED]","password":"Bug-Test-Pass-2026!"}'
```

Response: `HTTP/1.1 403 Forbidden`
```json
{"error":"Please verify your email before signing in. Check your inbox or request a new link.","code":"EMAIL_NOT_VERIFIED"}
```

This is the inconsistency: `/auth/login` enforces verification, `/auth/register` does not.

## Why this is real and not a misread

The platform *does* have a verification system — these endpoints exist and behave as expected:
- `POST /api/v1/auth/resend-verification` → returns `204 No Content` (accepted, email presumably sent)
- `POST /api/v1/auth/verify-email` → returns `404` for an invalid token (route exists, validates real tokens)

So the feature is wired up; it's just not gating the registration path. Also worth flagging: `GET /api/v1/me` doesn't even return an `emailVerified` field in the `user` object, which suggests the server isn't surfacing verification state anywhere the client could act on it.

## Impact

- **Account creation with attacker-controlled email:** anyone can spin up a tenant/org and consume plan quota (monitor slots, monthly checks, 1 GiB/month log ingest on free tier) without ever proving email ownership.
- **Full owner-level write access pre-verification:** an unverified `owner` token can create/update/delete monitors and status pages, mint PATs (`tokens:write`), set alert channels, etc. — anything an owner can do. Worst case, an attacker could mint a PAT for headless persistence, or point monitors at targets in a way that the SSRF guard may not catch.
- **The login gate is misleading:** it gives the impression verification is enforced, when it's only enforced on *re-login*, not on the session that matters most (the first one, where the user is actively in the app).
- **Minor:** plan + quota info is returned to unverified accounts via `/me`.

## Suggested fix

Pick one, but the goal is to make registration and login consistent:

- **Preferred:** don't issue a usable `accessToken` from `/auth/register`. Return `202 Accepted` with a "check your email" message and require the user to verify via `/auth/verify-email` before they can sign in. This matches the login behavior already in place and removes the inconsistency.
- **Alternative (keep instant access but lock it down):** if the product genuinely wants instant access, add an `emailVerified: boolean` claim to the JWT and run a middleware that rejects (or read-only-restricts) any request with `emailVerified: false`, except for `verify-email`, `resend-verification`, `logout`, and `GET /me`. Surface `emailVerified` in `GET /me` so the dashboard can show a "verify your email" banner instead of silently letting the user in.

Either way, `GET /me` should return `emailVerified`, and the dashboard should gate `/monitors` and other feature routes on it.
