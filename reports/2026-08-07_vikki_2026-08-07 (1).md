## Bug 1 — 500 Internal Server Error on non-numeric entity ID (unhandled exception)

**Severity:** Critical
**Type:** Unhandled Exception / API Contract Violation
**Status:** Confirmed

### What happened
When sending a request with a non-numeric string (e.g., `abc`) as the entity `{id}` path parameter to the Context endpoints, the server crashes with an unhandled exception and returns an `HTTP 500 Internal Server Error` instead of a validation error.

---

### What I tested
I sent HTTP `GET` requests using invalid data types for the `{id}` parameter against the Context endpoints with full token scope (`*`):

* **Tested Endpoints:**
  * `GET /api/v1/context/entity/{id}`
  * `GET /api/v1/context/entity/{id}/neighborhood`
* **Reproduction Request:**
  ```http
  GET /api/v1/context/entity/abc HTTP/1.1
  Host: api.24observe.com
  Authorization: Bearer <TOKEN_ORG_157>
  ```
* **Actual Result:**
  ```http
  HTTP/1.1 500 Internal Server Error
  Content-Type: application/json

  {
    "error": "Internal server error"
  }
  ```
* **Expected Result:**
  ```http
  HTTP/1.1 400 Bad Request
  Content-Type: application/json

  {
    "error": "Invalid path parameter 'id'",
    "code": "VALIDATION_FAILED",
    "fields": [
      {
        "field": "id",
        "message": "Expected integer, received string"
      }
    ]
  }
  ```

---

### Why this matters
1. **Database Query Failure:** The input hits the database query layer without being validated or coerced into an integer, causing an uncaught query failure/exception inside the backend logic.
2. **API Specification & Contract Violation:** The API contract dictates that client-side input errors must yield standard `4xx` response envelopes containing a stable, programmatic `code` key. Returning a generic 500 breaks this contract.
3. **Agent Loop Exhaustion / DoS Risk:** Autonomous agents or automated HTTP clients encountering a `500 Internal Server Error` treat the error as transient and trigger automatic retry loops. A single malformed request can lead to a client continually hammering the backend server.

---

### What the fix should look like
1. Validate `{id}` strictly at the route schema layer prior to calling the controller or database query logic.
2. If using Zod validation, apply schema coercion and strict type checking:
   ```typescript
   const pathParamSchema = z.object({
     id: z.coerce.number().int().positive()
   });
   ```
3. Return an `HTTP 400 Bad Request` containing a standard structured error envelope whenever route parameter parsing fails.
