Bug 1 — Logs page "From" date filter is not working: logs appear even when From date is set after all available logs

Severity: Medium
Type: Broken feature / date filter failure
Status: Confirmed (verified via API — BAD_TIME_RANGE error when from date is in the future with no to date)

What happened:

I opened the Logs page at https://login.24observe.com/logs. I set the "From" date to 06-08-2026 22:40 (a time in the future — the latest log available in the system is at 17:11:00 UTC). I expected the page to show zero results because the From date is AFTER all available logs. Instead, the page still displayed logs — logs from before 17:11:00 were shown, completely ignoring the From date filter.

The date filter is not working. When a user sets a From date that is after the most recent log, the filter is silently dropped and all logs are shown instead.

What I tested:

I reproduced the issue via the API to understand the root cause. The Logs page uses the endpoint:

  GET /api/v1/logs/search?from=<ISO timestamp>&to=<ISO timestamp>

Here are the API test results:


--- Test 1: from=2026-08-06T22:40:00Z&to=2026-08-06T23:00:00Z (both future) ---

Request:  GET /api/v1/logs/search?from=2026-08-06T22:40:00Z&to=2026-08-06T23:00:00Z
Response: 200 OK
Body:     {"events":[],"nextCursor":null,"tookMs":7,"facets":{}}

Expected: 200 OK with empty events array.
Actual:   Works correctly when BOTH from and to are provided, even if both are in the future.


--- Test 4: from=2026-08-06T17:10:00Z (past time, no to date) ---
Request:  GET /api/v1/logs/search?from=2026-08-06T17:10:00Z
Response: 200 OK, events from 17:21:08 down to 17:10:05

Expected: All events from 17:10:00 onward.
Actual:   Works correctly when from is a valid past time.



Root cause analysis:

The API has a validation bug in the /api/v1/logs/search endpoint:

1. When ONLY a `from` parameter is provided (no `to`), the API appears to
   calculate an implicit `to` as "now." If `from` > "now," the API rejects
   the request with BAD_TIME_RANGE instead of returning an empty result set.

2. The GUI (https://login.24observe.com/logs) receives this BAD_TIME_RANGE
   error and appears to fall back to showing unfiltered logs — or the GUI
   silently drops the from parameter and retries without it. Either way,
   the user sees logs they should not see.

3. When BOTH `from` and `to` are provided and both are in the future, the
   API correctly returns an empty events array. This proves the API CAN
   handle future time ranges — it just fails when only `from` is given.

Why this matters:

1. User confusion — the user sets a date filter expecting to see logs from
   that time onward. When logs from BEFORE that time appear, the user thinks
   the filter is broken or the data is wrong.

2. False data — if a user is investigating an incident and sets a specific
   time window, seeing logs from outside that window can lead to incorrect
   conclusions about when events occurred.

3. Silent failure — the GUI does not show an error message like "Invalid
   time range" to the user. It silently shows unfiltered data, so the user
   has no idea their filter was ignored.

4. Inconsistent behavior — the API behaves differently depending on whether
   `to` is provided or not. With `to`: returns empty. Without `to`: returns
   an error. This inconsistency is confusing for API consumers.

What the fix should look like:

1. The API should NOT return BAD_TIME_RANGE when `from` is in the future
   and no `to` is specified. Instead, it should return 200 OK with an
   empty events array: {"events":[],"nextCursor":null,"tookMs":...,"facets":{}}.

2. The API should handle the case where `from` > `to` gracefully — return
   200 OK with empty events, or return a clear, specific error message like
   "from date must be before to date" instead of the generic "invalid time
   range."

3. The GUI should display a clear message when the time filter returns zero
   results, such as "No logs found in the selected time range" — instead of
   silently falling back to unfiltered data.

4. The GUI should surface API errors to the user. If the API returns
   BAD_TIME_RANGE, the GUI should show an error toast or inline message
   rather than silently retrying without the filter.
