## BUG-035 — No Bulk Revoke for API Tokens
**Severity:** LOW · **Previous:** STILL PRESENT · **Today:** ❌ STILL PRESENT

```

## BUG-037 — Stored XSS Sink in Public Status Page Component Name
**Severity:** MEDIUM · **Previous:** CONFIRMED · **Today:** ❌ STILL PRESENT

Full attack chain reproduced live today:

1. Create monitor with HTML name (HTTP 201, id 704):
```
POST /api/v1/monitors/  {"name":"<img src=x onerror=alert(1)>","url":"https://example.com","type":"https","intervalSec":300,"timeoutMs":10000}
→ 201, "name":"<img src=x onerror=alert(1)>"   (stored verbatim)
```

2. Create public status page (HTTP 201, id 156, slug `xssrender-retest-001`):
```
POST /api/v1/status-pages/  {"title":"XSS Render Retest","slug":"xssrender-retest-001","isPublic":true}
→ 201
```

3. Attach component with same HTML payload as name (HTTP 201, id 54):
```
POST /api/v1/status-pages/156/components  {"monitorId":704,"name":"<img src=x onerror=alert(1)>"}
→ 201, "name":"<img src=x onerror=alert(1)>"   (echoed raw)
```

4. **Unauthenticated** public fetch — payload served verbatim, unescaped:
```
GET /api/v1/status-pages/public/xssrender-retest-001   (NO Authorization header)
→ 200, application/json; charset=utf-8, x-content-type-options: nosniff
   components[0].name = "<img src=x onerror=alert(1)>"
   monitors[0].name   = "<img src=x onerror=alert(1)>"
```

**Assessment (unchanged from original):** The API sets `application/json` + `nosniff`, so a browser fetching the JSON directly will not execute the payload. Execution still depends entirely on whether the status-page frontend renders `name` via `innerHTML`/`v-html`/`dangerouslySetInnerHTML`. The **stored-XSS sink at the API layer is still fully open** — injectable by any authenticated user, exposed publicly with no auth, and unescaped on output. No HTML-encoding or input rejection has been added.

**Verdict:** ❌ STILL PRESENT — no API-layer fix applied.

## BUG-038 — Oversized Payload Accepted in Monitor `description`
**Severity:** LOW · **Previous:** Open · **Today:** ❌ STILL PRESENT

```
POST /api/v1/monitors/  {"name":"bug038-oversized-desc","url":"https://example.com","type":"https",
                          "intervalSec":300,"timeoutMs":10000,
                          "description":"<1,000,000 × 'A'>"}
→ HTTP 201  (monitor id 702 created, 1 MB of 'A' persisted in one description field)
```

No per-field length cap on `description`. The OpenAPI schema for `POST /api/v1/monitors/` does **not** declare a `description` property at all (it is silently accepted), and the PATCH schema has no `maxLength` on it either. Only the global body-size limit (~1–2 MB) stops larger payloads.

**Verdict:** ❌ STILL PRESENT — no per-field cap added.

## BUG-042 — Monitor Reports `down` for `https://httpbin.org/status/200`

Created a fresh monitor against the same target and let the checker run:

```

```

```
GET /api/v1/monitors/701
→ "lastStatus":"down","consecutiveFailures":1,"lastCheckedAt":"2026-08-11T15:01:31.529Z"

The net effect is identical — the uptime badge for a brand-new monitor immediately reports failure on a target that returns 200 the vast majority of the time.

**Verdict:** ❌ STILL PRESENT — fresh monitor against `httpbin.org/status/200` immediately recorded `down`.
