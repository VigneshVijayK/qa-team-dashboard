# BUG-051 (Reopened) — GUI Test Alert Button Still Bypasses Rate Limit (Session-Cookie Path Not Keyed Per-Org)

**Severity:** MEDIUM
**Type:** Security / rate-limit bypass
**Originally Reported:** 2026-07-21
**Reopened:** 2026-08-12
**Status:** ❌ STILL PRESENT (partial fix only)

---

## Summary

A rate limit was added to `POST /api/v1/monitors/:id/test-alert`, but it is **keyed per auth credential (PAT hash)**, not per organization. As a result:

- ✅ The **PAT / API** path is now correctly throttled to 5 test alerts per ~60s window.
- ❌ The **GUI session-cookie** path (the actual attack surface described in the original bug) still sends a test alert on **every click**, because the session cookie draws from a separate rate-limit bucket that never intersects with the PAT bucket.

This is exactly the per-auth-method split the original BUG-051 hypothesis #2 warned about and asked to be fixed with per-org keying. That fix was not implemented.

---

## Reproduction

### Setup — fresh monitor with email alert

```bash
curl -X POST "https://api.24observe.com/api/v1/monitors" \
  -H "Authorization: Bearer obs_[REDACTED]" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "name": "bug051-test-email",
    "url": "https://example.com",
    "type": "https",
    "intervalSec": 300,
    "timeoutMs": 10000,
    "alertEmail": "[EMAIL REDACTED]"
  }'
```

**Response (201):**
```json
{
  "id": 705,
  "organizationId": 157,
  "name": "bug051-test-email",
  "alertEmail": "[EMAIL REDACTED]",
  "hasAlertSms": false,
  "hasAlertVoice": false,
  "..."
}
```

### Test 1 — PAT path IS rate-limited (5 per window)

Fired 7 sequential test-alert calls against monitor 705 via PAT:

```bash
for i in 1 2 3 4 5 6 7; do
  curl -X POST "https://api.24observe.com/api/v1/monitors/705/test-alert" \
    -H "Authorization: Bearer obs_[REDACTED]" \
    -H "Content-Type: application/json" \
    -d "{}" \
    -D - -o /dev/null -s -w "REQ $i -> %{http_code}\n"
done
```

**Results:**

| Req # | HTTP Status | `x-ratelimit-remaining` | `x-ratelimit-limit` | `x-plan-ratelimit-remaining` | Response Body |
|-------|-------------|--------------------------|----------------------|-------------------------------|----------------|
| 1 | 200 | 4 | 5 | 59 | `{"monitorId":705,"results":[{"channel":"email","attempted":true,"ok":true}]}` |
| 2 | 200 | 3 | 5 | 58 | `{"monitorId":705,"results":[{"channel":"email","attempted":true,"ok":true}]}` |
| 3 | 200 | 2 | 5 | 57 | `{"monitorId":705,"results":[{"channel":"email","attempted":true,"ok":true}]}` |

✅ PAT path: correctly throttled at 5 per ~60s window. Also consumes the shared plan bucket (`x-plan-ratelimit-remaining` decrements 59→55).

### Test 2 — the 5-limit is global across monitors (good)

After exhausting monitor 705's bucket, created a **second** monitor 706 and immediately called `test-alert` on it — it was also 429 without ever being tested:

```bash
# 705 exhausted, now hit fresh monitor 706:
curl -X POST "https://api.24observe.com/api/v1/monitors/706/test-alert" \
  -H "Authorization: Bearer obs_[REDACTED]" \
  -H "Content-Type: application/json" -d "{}"
```

**Result:**
```
MONITOR 705 -> 429 | testRL remaining: 0
MONITOR 706 -> 429 | testRL remaining: 0   ← fresh monitor, still blocked
```

✅ The limit is not per-monitor — it's a single shared bucket across all monitors for a given auth identity.

### Test 3 — GUI session-cookie path still sends on every click (NOT fixed)

Logged into the dashboard at `https://login.24observe.com` via Google OAuth, opened monitor 705's edit page, and clicked **"Send test alert"** repeatedly.

**Observed:** Every click sent the test email successfully. No throttling, no error message, no disabled-button state.

**Why this happens (confirmed via the account profile):**

```bash
curl "https://api.24observe.com/api/v1/me" \
  -H "Authorization: Bearer obs_[REDACTED]"
```

**Response (excerpt):**
```json
{
  "user": {
    "id": 157,
    "email": "[EMAIL REDACTED]",
    "hasPassword": false,
    "mfaEnabled": false
  },
  "organization": {
    "id": 157,
    "name": "[EMAIL REDACTED]'s Organization",
    "role": "owner"
  },
  "oauth": [
    { "provider": "google", "email": "[EMAIL REDACTED]", "linkedAt": "2026-08-04T12:15:31.153Z" }
  ]
}
```

`hasPassword: false` + `oauth: [{provider: "google"}]` ⇒ the GUI authenticates with a **session cookie** minted by Google OAuth, **not** with the PAT. The test-alert rate-limit bucket is keyed on the auth credential (PAT hash for PAT calls, session ID for cookie calls), so:

- PAT calls → bucket A (capped at 5).
- Session-cookie (GUI) calls → bucket B (uncapped / independent).

The two paths never share budget, so exhausting the PAT bucket does nothing to stop the GUI button, and vice versa.

---

## Root Cause

The `test-alert` rate-limit key is derived from the **auth credential**, not from the **organization**. Each distinct auth method (PAT vs session cookie) gets its own counter, so the limit only protects the path it was tested on (PAT). The GUI session-cookie path — the exact attack vector the original bug described (browser automation clicking the button) — is unaffected.

This is precisely the failure mode the original BUG-051 called out in its fix recommendation #2:

> *"if the GUI uses session cookie auth instead of PAT auth, the rate limit should be applied per-org (not per-auth-method) so both auth paths share the same 60-request budget."*

That per-org keying was not implemented.

---

## Impact

1. **Rate-limit bypass is still exploitable** via the GUI. An attacker (or a stuck button, or a browser-automation script) can click "Send test alert" hundreds of times and flood every configured channel — Slack, Discord, Telegram, PagerDuty, Opsgenie, email, SMS, voice — without ever hitting the 5-per-window cap that now protects the PAT path.
2. **Each click sends real outbound messages** to third-party alert integrations, so the abuse has real-world cost and noise consequences (Slack spam, PagerDuty incidents, SMS/voice spend).
3. **Inconsistent behavior persists:** the "Recent checks" panel on the same page is rate-limited (shows "Plan API rate limit reached"), while the test-alert button on the same page is not. This is the same inconsistency reported in the original bug.

## Recommended Fix

Key the `test-alert` rate-limit counter on the **organization**, not the auth credential:

```
# Current (vulnerable):
key = "testalert:" + hash(auth_credential)        # PAT and session cookie get separate buckets

# Fixed:
key = "testalert:org:" + orgId                     # all auth paths for the org share one bucket
```

Concretely:
1. Resolve `orgId` from whichever auth context is in play (PAT → PAT's org; session cookie → session's org).
2. Use `testalert:org:{orgId}` (plus the window) as the rate-limit key for `POST /monitors/:id/test-alert`.
3. Apply the same `testalert:org:{orgId}` key for both PAT and session-cookie auth so they draw from a single 5-per-window budget.
4. Optionally also enforce a lower per-monitor sub-cap (e.g. 3/monitor/window) to stop one monitor's button from starving the rest of the org's budget — but the org-level key is the mandatory part that closes the bypass.

Once keyed per-org, exhausting the budget via the GUI button will also throttle the API, and vice versa — closing the bypass described in the original BUG-051.
