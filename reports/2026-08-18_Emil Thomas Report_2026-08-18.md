Bug 1 — Cloud OTLP redaction is partial: password= and token= leak in cleartext

Severity: High
Type: Secret exposure / incomplete redaction
Status: Confirmed (live ingest + query, 2026-08-18, marker redact-reverify-6ca496058d)

What happened:

I shipped this log body straight to the cloud OTLP API (POST /api/v1/otlp/v1/logs):

  user=alice password=supersecret123456 api_key=AKIAIOSFODNN7EXAMPLE token=ghp_abcdef0123456789abcdef Authorization: Bearer obs_[REDACTED]

When I queried it back (host="redact-reverify-6ca496058d-host"), the stored message was:

  user=alice password=supersecret123456 api_key=[REDACTED:secret] token=ghp_abcdef0123456789abcdef Authorization: Bearer [REDACTED:secret]

What got scrubbed vs what leaked:

  Secret in the log                         After ingest                         Result
  api_key=AKIAIOSFODNN7EXAMPLE              api_key=[REDACTED:secret]            Scrubbed
  Authorization: Bearer obs_SECRET...      Bearer [REDACTED:secret]             Scrubbed
  password=supersecret123456               still password=supersecret123456     Leaked
  token=ghp_abcdef0123456789abcdef         still token=ghp_...                  Leaked

Simple takeaway: redaction exists, but it is incomplete. AWS-looking api_key values and Bearer headers are scrubbed; plaintext password= and GitHub-style token= values are stored and queryable.

What I tested:

1. Built OTLP resourceLogs payload with the bait string above and unique host/marker (service=redact-reverify, attrs.qa.marker=redact-reverify-6ca496058d).
2. POST /api/v1/otlp/v1/logs → 200 {}.
3. Polled POST /api/v1/logs/query with host="<marker>-host" — row returned on first attempt (~5s; 1/6 poll attempts).
4. Scanned stored message + full row JSON for each cleartext secret.
5. Result: leaked=['password', 'token']; scrubbed=['api_key', 'authorization_bearer']; REDACTED markers present for the scrubbed fields.
6. Compared against the host Alloy redact block (from live bootstrap configs). Sensor-side statements include BOTH:
     - `\\bgh[pousr]_[A-Za-z0-9]{36,}\\b` → [REDACTED:github]
     - `(?i)\\b(password|passwd|secret|api[_-]?key|token)[\\"\\s:=]+[^\\s\\"]{6,}` → [REDACTED:kv-secret]
   So a host Alloy path that ran those rules should have scrubbed password= and token=. This test bypassed Alloy and hit cloud OTLP directly — proving the server-side rule set is weaker / different.

Evidence:

  MARKER: redact-reverify-6ca496058d
  HOST:   redact-reverify-6ca496058d-host
  STATUS: CONFIRMED_PARTIAL_REDACTION_GAP
  ingest: POST /api/v1/otlp/v1/logs → 200 {}
  query:  rows=1 on attempt 1 (~5s)
  message (stored): user=alice password=supersecret123456 api_key=[REDACTED:secret] token=ghp_abcdef0123456789abcdef Authorization: Bearer [REDACTED:secret]
  full row snippet:
    {"ts_ms":"1787049408680","level":"info","service":"redact-reverify","source":"otlp",
     "host":"redact-reverify-6ca496058d-host",
     "message":"user=alice password=supersecret123456 api_key=[REDACTED:secret] token=ghp_abcdef0123456789abcdef Authorization: Bearer [REDACTED:secret]",
     "attrs":"{\"qa.marker\":\"redact-reverify-6ca496058d\",\"otel.scope.name\":\"redact-reverify\",\"otel.scope.version\":\"1.0.0\"}"}
  cleartext scan: LEAK password, OK api_key, LEAK token, OK authorization_bearer
  log file: redact_reverify_2026-08-18.log

Note on sensor-side vs cloud-side:
- Host Alloy configs include an otelcol.processor.transform "redact" block with a kv-secret rule that should match password= / token= patterns (and a separate github PAT prefix rule).
- This test hit the cloud OTLP API directly, so the gap is in server-side redaction (or a weaker/different rule set than the Alloy processor). Either path that stores cleartext passwords/tokens is a High finding for a security-oriented log platform.
- Combined with Bug 7 (broad execve audit rules), argv secrets such as `curl -H Authorization:...` or `mysql -p...` can land in audit.log, ship via Alloy, and still be searchable in cleartext if cloud redaction misses them.

Why this matters:

1. Customers (and attackers) routinely land password= and token= strings in application/auth logs.
2. Partial redaction creates false confidence — operators see [REDACTED:secret] nearby and may assume all secrets are scrubbed.
3. Cleartext credentials in the searchable log store expand blast radius on account compromise and complicate compliance (secret sprawl).
4. GitHub PATs (ghp_…) and passwords are high-value secrets; leaving them queryable is worse than not advertising redaction at all.
5. Direct cloud OTLP shippers (apps, sidecars, collectors that skip host Alloy) get no benefit from the stronger sensor-side rule set.

What the fix should look like:

1. Align cloud OTLP redaction with (or stronger than) the Alloy kv-secret rule: password|passwd|secret|api[_-]?key|token followed by separator + value.
2. Explicitly cover common token prefixes (ghp_, gho_, github_pat_, xoxb-, sk-, obs_, etc.) even without a key= prefix — matching the Alloy github/slack/llm rules already shipped to sensors.
3. Add a regression test: ship the exact bait string above → query → assert password and token cleartext absent.
4. Document what is and is not redacted so customers do not assume full secret scrubbing.
5. Prefer one shared redaction policy source for Alloy generator and cloud ingest so the two paths cannot drift again.

Bug 2 — snmp_exporter downloaded from GitHub without signature/checksum verification

Severity: High
Type: Supply-chain / binary authenticity
Status: Confirmed (install.sh static analysis + upstream sha256sums.txt probe, 2026-08-18)

What happened:

The snmp profile's setup_snmp() downloads Prometheus snmp_exporter from GitHub Releases over HTTPS:

  curl -fsSL "https://github.com/prometheus/snmp_exporter/releases/download/v${SNMP_EXPORTER_VER}/snmp_exporter-${SNMP_EXPORTER_VER}.linux-${a}.tar.gz"

It then untars and installs the binary to /usr/local/bin/snmp_exporter with no sha256sum, GPG, cosign, or minisign verification. Upstream publishes sha256sums.txt for the same release (HTTP 200, usable digests present), but install.sh does not fetch or check it.

This contrasts with Alloy, which is installed from Grafana's signed apt/rpm repositories (signed-by / gpgcheck=1 / repo_gpgcheck=1).

What I tested:

1. Grepped install.sh for snmp download + verify ops (sha256|checksum|minisign|cosign|gpg --verify) → download present, verify ops NONE.
2. Fetched upstream sha256sums.txt for v0.26.0 → HTTP 200, 4162 bytes, contains per-artifact digests. Sample lines observed:
     5e2bd55baa91e321b684c3578db7f194a53b454be381718bfd1ea2551d3c07e1  snmp_exporter-0.26.0.aix-ppc64.tar.gz
     93159dc53f2400f75d2a4bae5a188b9e59550963c6c56464913df914dfb9f319  snmp_exporter-0.26.0.darwin-amd64.tar.gz
     … (linux-amd64 / linux-arm64 digests also present in the same file)
   ALT path SHA256SUMS → HTTP 404 (only sha256sums.txt is valid).
3. Confirmed via _confirm_findings.py: VERDICT CONFIRMED HIGH — HTTPS download only; no checksum/sig check.
4. Positive control contrast: Alloy apt signed-by + rpm gpgcheck = PASS. snmp_exporter listen address remains 127.0.0.1:9116 (loopback) with MemoryMax=150M — good runtime hygiene, but does not mitigate unsigned download.

Evidence:

  SNMP_EXPORTER_VER=0.26.0
  download present: True
  download snippet: curl -fsSL "https://github.com/prometheus/snmp_exporter/releases/download/v${SNMP_EXPORTER_VER}/snmp_exporter-${SNMP_EXPORTER_VER}.linux-${a}.tar.gz"
  verify ops in install.sh: NONE
  upstream sha256sums.txt: HTTP 200 (digests available but unused)
  Alloy signed apt/rpm: PASS (control contrast)
  install path: /usr/local/bin/snmp_exporter + systemd unit snmp_exporter.service (Description carries "24observe")
  ownership marker: /etc/alloy/.owns-snmp-exporter (uninstall symmetry improved vs older BUG-056/068; authenticity still unverified at download)

Why this matters:

1. A compromised GitHub release asset, CDN cache poison, or MITM that still presents HTTPS could land a trojaned exporter on customer hosts.
2. snmp_exporter runs as a local systemd service; a malicious binary gets persistent code execution on the sensor host.
3. The product already demonstrates the right pattern for Alloy (signed repo) — snmp is the unsigned exception on the same installer.
4. Security customers evaluating supply chain will treat "HTTPS only, no digest" as a High finding.

What the fix should look like:

1. Fetch upstream sha256sums.txt (or pinned digest in install.sh) and verify before install.
2. Prefer cosign/sigstore or GitHub attestation verify if available for the release.
3. Fail closed on mismatch; do not silently continue.
4. Add CI/install test that asserts checksum verification runs for snmp_exporter.

Bug 3 — Generated alloyConfig has no cryptographic signature or digest

Severity: High
Type: Supply-chain / config authenticity weakness
Status: Confirmed (docker re-test + Linux confirm run, 2026-08-18)

What happened:

POST /api/v1/sensors/bootstrap returns:

  alloyConfig, findingsEnabled, hostId, ingestToken, otlpEndpoint, redact

There is no signature, digest, checksum, MAC, or JWT field binding the config. install.sh writes alloyConfig verbatim to /etc/alloy/config.alloy after Bearer enroll succeeds. Authenticity = TLS + Bearer only.

Confirmed for:
- docker profile bootstrap (marker docker-sensor-qa-7a1648decd) — baseline 4931 bytes, docker 5280 bytes
- Linux confirm / multi-profile bootstrap (linux-sensor-qa-4da1a26a1d):
    baseline 4931 | auditd 5325 | syslog 5317 | snmp 5850 bytes
  keys identical across profiles; no sig fields on any response

What I tested:

1. Enroll + bootstrap with and without profiles (docker harness + _confirm_findings.py + linux harness).
2. Inspected response keys for sig/sign/hash/digest/checksum/mac/jwt → none.
3. Confirmed install.sh path writes config verbatim with no verify step.
4. Docker harness summary for this gap alone: FAILs 1/24 (HIGH) on unsigned config within that harness.

Evidence:

  bootstrap keys=['alloyConfig', 'findingsEnabled', 'hostId', 'ingestToken', 'otlpEndpoint', 'redact']
  signature-like fields: NONE
  install.sh writes alloyConfig verbatim to disk: True
  alloyConfig present: True (e.g. confirm run bytes=4931 baseline)
  docker re-test: hostId cleanup deleted 177/178; marker docker-sensor-qa-7a1648decd
  Verdict: CONFIRMED HIGH — trust = TLS + Bearer only; no detached signature

Why this matters:

1. A stolen enroll token (or any path that can call bootstrap as that token) can deliver arbitrary Alloy config to the host with no independent integrity check.
2. Operators have no local digest to pin or audit "intended config."
3. Affects every Linux Sensor profile path that uses bootstrap alloyConfig (baseline, docker, auditd, syslog, snmp, nginx, …).
4. There is still no continuous signed policy channel after install — config refresh = re-run enroll/bootstrap over TLS+Bearer (noted as MED INFO in the Linux harness step 3d).

What the fix should look like:

1. Return sha256 (and/or signature) of alloyConfig + hostId + version in bootstrap.
2. Have install.sh verify before writing config.alloy.
3. Document signing keys and rotation.
4. Integration test: tampered config fails install.

Bug 4 — Docker profile requires host docker.sock access (docker-group ≈ root-equivalent)

Severity: Medium
Type: Host trust-boundary / privilege implication (not a classic container escape)
Status: Confirmed (live config + installer analysis, re-test 2026-08-18)

What happened:

Docker-profile alloyConfig uses:

  discovery.docker "containers" { host = "unix:///var/run/docker.sock" }
  loki.source.docker "containers" { host = "unix:///var/run/docker.sock" ... }

Alloy is a host systemd service (no sensor pod, no docker.sock volume mount, no --privileged). Docker does not force User=root. But Engine API via the socket typically means docker-group membership ≈ root-equivalent via privileged container spawn.

Profile is real: +349 bytes vs baseline; adds discovery.docker + loki.source.docker (saved as qa_docker_profile_docker-sensor-qa-7a1648decd.alloy).

Evidence (re-test docker-sensor-qa-7a1648decd):

  host= unix:///var/run/docker.sock (×2)
  install.sh docker.sock mount: False; privileged=False; host_ns=False
  docker elevates User=root: False (elevation gated to auditd||syslog)
  size delta: 349 bytes
  workspace inventory: Dockerfile/helm/compose/k8s-manifest all False
  resource caps still applied: MemoryMax=1G, MemoryHigh=512M, CPUQuota=75%
  no extra unsigned binary download for docker profile (unlike snmp)

Why this matters:

1. Not a container-escape-via-mounted-sock — there is no sensor container.
2. Enabling --profile=docker still expands local trust: Alloy must reach Docker Engine API.
3. Compromised Alloy/config with sock access is often host-root equivalent.
4. Operators may assume "container sensor" implies isolated privileges; product reality is host Alloy + sock.

What the fix should look like:

1. Document the docker-group / socket trust boundary clearly in Hosts UI + install output.
2. Prefer rootless Docker, docker-socket-proxy (read/log-only), or narrower collection.
3. Keep current PASS that docker does not force User=root.

Bug 5 — auditd/syslog profiles run the Sensor as root for life (no post-init drop)

Severity: Medium
Type: Privilege longevity / least-privilege gap
Status: Confirmed (install.sh analysis, 2026-08-18)

What happened:

When --profile=auditd or --profile=syslog is present, enroll_and_configure writes a systemd drop-in with:

  User=root
  Group=root
  AmbientCapabilities=CAP_NET_BIND_SERVICE

Elevation is justified (audit.log is root:root 0600; syslog binds :514). There is no mechanism to drop privileges after open/bind — the Alloy service remains root for its entire lifetime. install.sh prints a WARN acknowledging the exception.

What I tested:

1. Elevation gate: has_profile auditd || has_profile syslog → User=root.
2. Searched install.sh for post-init drop / DynamicUser / capability bounding after start → none.
3. _confirm_findings.py: post-init privilege drop mechanism: False.
4. Positive contrasts reconfirmed:
     - CAP_SYS_ADMIN / CAP_BPF / CAP_NET_ADMIN not requested (only CAP_NET_BIND_SERVICE)
     - docker/snmp/baseline do not force User=root
     - Alloy configs themselves do not demand root; privilege is left to the systemd drop-in

Why this matters:

1. Root for life widens impact of any Alloy RCE / config abuse on auditd/syslog hosts.
2. CAP_NET_BIND_SERVICE alone might suffice for :514 after a privileged bind+drop pattern; reading audit.log may need capabilities or group ACLs instead of full root.
3. Documented WARN in installer is good; least-privilege hardening is still missing.
4. Combined with Bug 6 (0.0.0.0:514), a syslog-facing bug becomes higher impact.

What the fix should look like:

1. Prefer file ACLs / audit group for audit.log and bind + drop (or systemd socket activation) for :514.
2. If root is unavoidable at start, drop to alloy user after resources are opened where Alloy/runtime allows.
3. Document residual risk when profiles force root.

Bug 6 — Syslog profile listens on 0.0.0.0:514 (UDP + TCP)

Severity: Medium
Type: Network exposure / attack surface
Status: Confirmed (live syslog bootstrap, 2026-08-18)

What happened:

Syslog-profile alloyConfig includes loki.source.syslog listeners on:

  address = "0.0.0.0:514" (UDP)
  address = "0.0.0.0:514" (TCP)

Live bootstrap (cfg_bytes=5317) returned both listeners on 0.0.0.0:514. Binding all interfaces requires elevated privileges and exposes a network syslog intake wherever the host firewall allows.

What I tested:

1. Fresh enroll + bootstrap with profiles=["syslog"] (confirm run host qa-syslog-4681d14e; also linux-sensor-qa-4da1a26a1d-syslog).
2. Parsed listener address= fields → ['0.0.0.0:514', '0.0.0.0:514'].
3. Contrast: local OTLP receiver stays on 127.0.0.1:4317/4318; snmp_exporter on 127.0.0.1:9116 — only syslog is world-bind by default.
4. Verdict: CONFIRMED MED — UDP+TCP on 0.0.0.0:514; host firewall required.

Why this matters:

1. World-open syslog receivers are a classic amplification / spoof / log-injection surface.
2. Exposure depends on host firewall — many cloud images leave :514 reachable inside VPC or more broadly.
3. Combined with Bug 5 (root for life), a syslog-facing bug is higher impact.
4. Combined with Bug 1 (partial cloud redaction), injected syslog lines containing secrets may be stored searchable.

What the fix should look like:

1. Default to 127.0.0.1:514 or a documented management interface; make 0.0.0.0 opt-in.
2. Document required firewall rules in the syslog profile install output.
3. Consider rate limits / allowlists at the listener.

Bug 7 — Broad execve audit rules (high-volume telemetry / noise / PII)

Severity: Medium
Type: Telemetry volume / privacy / ops risk (not direct RCE)
Status: Confirmed (install.sh 24observe.rules, 2026-08-18)

What happened:

setup_auditd() drops /etc/audit/rules.d/24observe.rules including:

  -a always,exit -F arch=b64 -S execve -k exec
  -a always,exit -F arch=b32 -S execve -k exec

plus watches on /etc/passwd, /etc/group, /etc/shadow, /etc/sudoers, /etc/sudoers.d/, /etc/ssh/sshd_config, /root/.ssh/, /etc/crontab, /etc/cron.d/.

Logging every execve is powerful for security analytics but generates high-volume audit traffic, can include sensitive command lines, and increases retention/cost/noise.

What I tested:

1. Extracted rules from install.sh (and confirmed identical content in live confirm + linux harness step 2b).
2. watch paths (9) + execve rules (2) confirmed.
3. Uninstall path now removes 24observe.rules and reloads audit rules (improved vs older incomplete-uninstall bugs) — still worth regression coverage.
4. Verdict: CONFIRMED MED — high-volume telemetry / noise/PII consideration (not RCE).

Why this matters:

1. Busy hosts can produce very large audit.log volume → disk, Alloy backlog, and ingest cost.
2. execve records often contain secrets in argv (curl -H Authorization:..., mysql -p...).
3. Combined with Bug 1 (partial cloud redaction), argv secrets may land searchable in cleartext.
4. Prior related observation (2026-08-14): audit logs were also poorly structured for query (key=value left inside message). Volume + weak structure + weak redaction compounds SIEM usefulness issues.

What the fix should look like:

1. Make always,exit execve opt-in or scoped (uid filters, exclude noisy paths).
2. Keep identity/privilege/ssh watches as the default high-signal set.
3. Document volume expectations and redact/exclude guidance for argv secrets.
4. Ensure uninstall continues to remove 24observe.rules and reload audit rules (already improved vs older bugs).
5. Pair with Bug 1 fix so any remaining argv secrets are scrubbed server-side.
